# Context Notes: 재고 관리 웹앱 1차
결정과 이유를 발생한 순서대로 이어서 적는다. 기각한 대안도 남긴다.

## 2026-10-26 인터뷰·문서 단계
- 수량 변경 방식은 이력 기반으로 확정. 기각한 안은 현재 수량 덮어쓰기. 이유는 원인 추적이 불가능해서.
- `stock` 캐시 테이블을 둔다. 기각한 안은 조회 때마다 이력 합산. 이유는 목록·검색 성능. 일치는 RPC 단일 쓰기 경로와 `verify_stock_ledger()`로 보장.
- 이동은 이력 두 행(출발 감소, 도착 증가)에 같은 `group_id`. 기각한 안은 이력 한 행에 출발·도착 두 위치 열. 이유는 위치별 이력 조회와 합 검증을 한 규칙으로 쓰려고.
- 위치 코드는 전체에서 유일. 기각한 안은 상위 안에서만 유일. 이유는 QR 하나로 위치를 특정해야 해서.
- 가져오기는 오류가 있으면 전체 거절(사용자 승인). 기각한 안은 유효 행만 부분 반영. 이유는 반영 범위 추적이 어려워서.
- C1 승인으로 1차에 단건 조정(R21)을 포함. 일괄 실사 화면(R22)만 2차.
- 사용자가 "숭안", "승인"을 연달아 보냈다. spec 승인으로 처리했다. plan.md 승인은 아직 받지 않았다.

## 2026-10-26 plan 작성 중 채운 빈칸 (spec이 말하지 않은 것)
- 가져오기에서 이미 있는 위치 코드는 이름·상위를 바꾸지 않고 "기존"으로 건너뜀. spec R31이 품목만 갱신을 규정했기 때문. 사용자가 위치 갱신도 원하면 spec 수정 필요.
- 같은 (SKU, 위치코드) 중복 행, 파일 안 바코드 충돌을 오류로 추가. 검증 누락 방지.
- 정정은 정정 행 자체에는 불가, 이동 행은 같은 `group_id` 두 행을 함께 정정. 한쪽만 정정하면 이동이 반쪽이 되어서.
- 정정 사유는 선택. 조정만 사유 필수(spec R21).
- 이력 내보내기는 최대 50,000행. Vercel 응답 본문 4.5MB 한도와 시간 때문. 한도에 걸리면 보고하고 조정.
- 서비스 롤 키는 쓰지 않는다. 쓰기는 `security definer` RPC와 RLS로만.
- 1차 RLS는 로그인 사용자 전원에게 품목·위치 쓰기 허용. 2차 role 분기 전까지 계정 1개 가정.
- 테스트는 가져오기 검증 순수 함수 1파일만 저장소에 남긴다. SQL 검증은 임시 스크립트로 하고 남기지 않는다. 기각한 안은 pgTAP·E2E 상시 테스트. 이유는 1차 범위와 팀 규모 대비 과함.

## 2026-10-26 구현 중 결정
- Supabase 프로젝트 inventory(ref ikbzdqkjdvaatqmrmqzz, 서울, Free 플랜) 생성. 기존 dev 프로젝트에 합치는 안은 기각. 이유는 테이블과 profiles 트리거가 다른 앱과 섞이기 때문.
- search_items 에 include_archived 인자 추가(Advisor가 W2 결과를 읽고 직접 수정). W3의 "보관 포함" 필터와 W4 선택지 숨김을 같은 함수로 처리하려고.
- 마이그레이션은 MCP apply_migration 으로 적용했고, 적용한 SQL 은 저장소 파일에서 주석만 뺀 사본이다. 동작은 같다.
- 정정(reverse_movement)은 보관된 품목·위치에는 거절. 보관된 대상에 수량이 되살아나는 것을 막으려는 의도로 유지. 복원 후 정정하면 된다.
- 교착 가능성(같은 품목의 A→B, B→A 이동 동시 입력)과 동시 순환 이동은 데이터가 깨지지 않고 사용자가 소수여서 고치지 않음. 계정이 늘면 위치 id 순서로 잠그는 방식을 검토.
- 신규 조합에 수량 0을 적은 가져오기 행은 stocks_ignored 로 센다. 건수 표시만 영향.
- import_apply 는 같은 SKU의 중복 행 중 하나를 임의로 쓴다. 중복 검출은 W5의 validate.ts 책임. W5 검증 때 확인할 것.
- 검증 방식. S1에서 한 트랜잭션 DO 블록으로 시나리오를 돌리고 마지막에 예외로 롤백해 테스트 데이터를 남기지 않았다. 롤백 뒤 모든 테이블 0건 확인.
- 코드 리뷰 지적 중 스멜 항목(포커스 링 클래스 반복, Supabase 쿠키 어댑터 중복, search_items SELECT 중복, 로그인·수량 검증 블록 반복)은 1차 범위에서 고치지 않음. 이유는 동작 변경이 없고 후속 Worker 작업과 파일이 겹치기 때문.
- 설정 파일의 영문 주석(eslint.config.mjs, next.config.ts)은 create-next-app 생성 문구라 그대로 둠.

## 2026-10-26 W3~W5 리뷰 결정
- 작업자 표시 문제(모든 이력이 "알 수 없음")는 앱에서 auth.users 를 조회하는 대신 트리거 기본값(0004)으로 해결. 기각한 안은 서버에서 service role 로 auth.users 조회. 이유는 서비스 롤 키를 앱에 두지 않는다는 원칙.
- 화면 오류 문구에 DB 메시지를 노출하던 곳(history, move 페이지)은 일반 문구로 교체. RPC 오류(한국어로 만든 메시지)는 사용자에게 의미가 있어서 그대로 보여준다. 후속으로 예기치 않은 영문 오류를 걸러내는 방안을 검토.
- 이력 날짜 필터는 형식만이 아니라 달력에 있는 날짜인지 확인한다.
- 이동 묶음이 페이지 경계에 걸리면 양쪽 페이지에 나올 수 있음. 건수가 적은 소규모 운영이라 수정하지 않음.
- 라벨 표(유형)가 history, 품목 상세, 내보내기 3곳에 중복. 값이 일부 다르다(이동 vs 이동 출고/입고). 동작 영향이 작아 공용화는 후속으로 미룬다.
- 검색 라벨에 "바코드"를 추가(RPC가 바코드도 검색하기 때문).
